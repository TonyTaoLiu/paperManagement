# Goal 模式开发提示词

> 用法：在新的云端会话中，把下面分隔线之间的内容整体粘贴，作为 goal 模式的目标。

---

## 目标

按照仓库中的 `docs/项目开发文档.md`，把 **PaperMind（论文记忆库）** 从零开发完成，交付一个**无需任何 API key、一键启动**的本地论文管理应用。持续推进，直到第 9 节所有里程碑（M0 → M0.5 → M1 → M2 → M3 → M4 → M5）的验收标准都满足为止。中途不要停下来等我确认，除非遇到下文"何时找我"列出的情况。

## 开始前

1. 如果当前分支没有 `docs/项目开发文档.md`，先执行 `git fetch origin claude/eloquent-goldberg-2h6ae0 && git merge origin/claude/eloquent-goldberg-2h6ae0` 拿到文档。
2. **完整阅读** `docs/项目开发文档.md`（尤其是第 3–9 节和附录 A、B）、`论文总结记录.md`、`论文总结要求.txt`。文档是需求的唯一依据；发现文档有矛盾或不可行之处，自行做出合理决定，并记录到进度文件的"决策记录"里。
3. 创建 `docs/开发进度.md`，包含：里程碑清单（勾选状态）、当前正在做什么、决策记录、已知问题、下一步。**每完成一个子任务就更新它并提交**。上下文被压缩或会话中断后，先读这个文件再继续。

## 已知环境事实（已实测，不用重复排查）

- 4 核 CPU、15 GB 内存、无 GPU，约 30 GB 可用磁盘；已装 Python 3.13、uv、Node 22、npm、git、gcc、cmake。
- 网络可访问：PyPI、npm、huggingface.co 及 `*.hf.co`（模型下载可用）、OpenAlex、arXiv、bioRxiv/medRxiv、Crossref、PubMed；Semantic Scholar 会返回 429 限流，需要退避重试。
- **GitHub Release / API 下载被拦截（403），但 `git clone` 可用**：云端用源码编译 llama.cpp 得到 `llama-server`（见文档 7.3）。
- 没有任何 LLM API key。**所有功能必须在内置本地模型下可用**；云端 API 只是可选增强，测试不得依赖它。
- 只能在 Linux 上直接运行；Windows/macOS 的启动脚本用 GitHub Actions（`windows-latest`、`macos-latest`）做冒烟测试，通过 GitHub MCP 工具查看运行结果和日志。

## 关键技术决定（文档已写明，必须遵守）

- 后端 Python + FastAPI + SQLite（FTS5）；前端 Vue 3 + Vite + TypeScript + Naive UI，图谱用 Cytoscape.js，图表用 ECharts；前端构建产物提交到仓库，用户无需 Node。
- 本地模型运行时 = 应用自行管理的 llama.cpp `llama-server` 子进程（生成、嵌入各一个），通过 OpenAI 兼容接口调用；**不要用 PyPI 的 llama-cpp-python，不要引入 PyTorch**。生成时用 JSON Schema 约束输出。
- 模型文件运行时下载到 `data/models/`，绝不提交进 git；`data/` 加入 `.gitignore`。
- 代码、注释、提交信息用英文；界面文字和文档用中文。

## 执行顺序与要求

1. **M0 骨架**：项目结构（见文档 4.3）、`pyproject.toml` + `uv.lock`、FastAPI 托管静态前端、设置页、`start.sh` / `start.command` / `start.bat`、GitHub Actions 三平台冒烟测试（启动服务 → 请求健康检查接口 → 退出）。
2. **M0.5 模型运行时与选型**：实现 llama-server 获取（Release 下载 → 源码编译 → 手动指定，三级回退）、进程管理、带进度和镜像的模型下载器、统一的 LLM/嵌入客户端。然后按文档 7.4 实测候选模型：
   - 先用 5 篇论文快速筛选全部候选，再让前 2–3 名跑完全部 19 篇；
   - 测完一个模型就删掉它的文件，保证磁盘够用；
   - 长时间任务放后台运行，不要干等；
   - 结果（真实数字）写入 `docs/模型评测.md`，据此确定 8 GB / 16 GB 两档默认模型。
3. **M1 → M5**：严格按文档第 9 节的内容和验收标准推进。M1 的硬性验收：导入 `论文总结记录.md` 得到 19 篇论文，第 04 轮并入第 05 轮，第 07/09/11/12/19 轮作为追问挂到对应论文，第 01/27 轮识别为非论文，重复导入不产生重复。M2 用附录 A 作为评测集，并把分类准确率写进 `docs/模型评测.md`。

## 质量要求

- 每个里程碑都要有 pytest 测试；用 `论文总结记录.md` 作为回归测试样例。单元测试可以用录制好的模型响应，但**评测数字和验收结论必须来自真实运行**，不得编造或估算后当作实测结果。
- 每个里程碑结束前：运行全部测试和 lint（ruff），启动应用，用 Playwright 截图检查主要页面（截图存到 `docs/screenshots/`），确认没有报错。
- 小步提交，每完成一个子任务就提交并推送到你被指定的开发分支；推送前确认测试通过。
- 不扩大范围：文档里标注 P2/P3 的功能放在 M5 及以后，前面的里程碑没完成之前不要做。
- 遇到外部问题（某个模型无法加载、某个 API 不可用），记录到"已知问题"，选一个可行的替代方案继续推进，不要卡住。

## 何时找我

只有以下情况才停下来问我：需要我提供账号或密钥；需要我在自己的 Windows/macOS 电脑上做验证；文档中的需求有歧义且两种理解会导致明显不同的产品。其他问题自行决策并记录。

## 完成标准

- 第 9 节全部里程碑验收通过，`docs/开发进度.md` 全部勾选；
- 三平台 GitHub Actions 冒烟测试为绿色；
- `README.md` 用中文写清楚：一键启动方法、硬件要求、两档模型说明、如何导入聊天记录、如何（可选）配置云端 API、数据存放位置与备份；
- `docs/模型评测.md` 包含真实评测数据和最终选型理由；
- 最后创建一个合并到 `main` 的 PR，描述中列出各里程碑的验收结果、已知问题，以及需要我在本机验证的事项。
